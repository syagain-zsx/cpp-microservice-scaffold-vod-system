## 1. 一句话介绍

> 一个 C++17 微服务化视频点播系统：Qt6 客户端 + 网关 + 用户/视频/文件/转码 5 个服务，
> 用 brpc + etcd 做服务通信与发现，MySQL/Redis/RabbitMQ/FastDFS/FFmpeg 做存储与异步处理。

## 2. 三分钟版（讲给面试官）

1. **背景**：课程项目是单体+脚本拼接，我把它重构成单仓库、统一 CMake 的微服务系统；
2. **架构**：客户端只连网关（HTTP+JSON），网关按 URL 做鉴权和路由，子服务通过 etcd 发现、brpc 调用；
3. **难点一：上传与转码解耦**——上传只落 FastDFS 并写库，转码通过 MQ 异步消费，避免长耗时阻塞请求；
4. **难点二：缓存一致性**——读走 Redis，写走 MySQL，计数类更新只改 Redis 并用延迟队列 30s 回写；
5. **难点三：可观测与降级**——ES 挂了搜索降级而不是服务崩溃；启动脚本按服务裁剪参数；
6. **结果**：5 个服务一键构建启动，端到端跑通登录→上传→转码→HLS 播放→点赞/弹幕→审核上下架，8 项单测 + 冒烟测试全绿。

## 3. 架构追问

**Q：为什么拆成 5 个服务？拆的依据是什么？**
按「业务能力 + 数据归属」拆：用户/视频/文件各自拥有数据，文件服务独占 FastDFS 访问，转码是 CPU 密集型且可异步。
网关只做横切（鉴权、路由、协议转换），不持有业务数据。

**Q：网关会不会成为瓶颈？**
会。当前是单进程 brpc，可水平扩展多个实例并用 etcd 注册；网关无状态，会话在 Redis，天然可扩。
再进一步可以做连接复用、限流、熔断。

**Q：服务之间怎么通信？为什么用 brpc 不用 gRPC？**
brpc 的 bthread + epoll 模型在高并发小包场景吞吐好，内置 HTTP/RPC 双协议、服务发现和内置监控页；
项目里既有 RPC 又有 HTTP（网关对外），brpc 一套搞定。gRPC 生态更好、跨语言更强，是备选。

**Q：etcd 做什么？为什么不用 ZooKeeper？**
服务注册与发现：`/服务名/实例ID → host:port`，租约保活，网关 watch 前缀感知上下线。
etcd 用 Raft、HTTP/gRPC API、TTL 租约天然适合容器环境；ZK 更重、运维复杂。

**Q：网关怎么知道某个服务有哪些节点？**
启动时 `watch` etcd 的 `/` 前缀（先拉全量再 watch），收到 put/delete 维护本地 `map<服务名, 节点列表>`；
选节点用轮询。服务下线时 watch 到 delete 事件即可摘除。

**Q：etcd 挂了会怎样？**
已建立的 RPC 不受影响（地址在内存）；但新节点无法注册、网关无法感知变化。
生产中 etcd 一般 3/5 节点集群；客户端可以加本地缓存 + 重试。

## 4. 消息队列追问

**Q：延迟队列怎么实现？**
两种方案：① RabbitMQ 的 `x-delayed-message` 插件；② 普通队列 + `x-message-ttl` + 死信交换机（DLX）。
项目用的是「声明常规队列时设置 TTL 和 DLX，消费者订阅 dlx_ 队列」的方式（`JianLiuMq::declare` 里自动建配套死信队列）。

**Q：消息会丢吗？怎么保证不丢？**
当前：发布用 `channel.publish`，没有 confirm，极端情况下可能丢；消费手动 ack。
改进：开启 publisher confirm + 持久化队列/消息 + 消费失败重试/死信。

**Q：重复消费怎么办？**
需要业务幂等。转码任务按 video_id 处理，重复执行会覆盖产物（幂等但浪费）；
计数回写可以改成「以 Redis 当前值为准」的覆盖写，天然幂等。

## 5. 缓存追问

**Q：缓存一致性怎么保证？**
- 读：cache-aside（先 Redis，未命中查 DB 回填）；
- 写：更新 DB 后删缓存（延迟 3s 删除，避免并发读写把旧值写回）；
- 计数类：只更新 Redis，把 key 投递到延迟 30s 的队列，由消费者回写 MySQL（写合并，降低 DB 压力）。

**Q：为什么延迟 3s/30s？**
3s 是给「删除缓存」留出并发窗口（先更库、后删缓存，避免读请求把旧值回填）；
30s 是计数回写的批量窗口，兼顾实时性与 DB 压力，可按业务调。

**Q：缓存穿透/击穿/雪崩？**
穿透：空结果也缓存（短 TTL）或布隆过滤器；击穿：热点 key 加互斥/逻辑过期；雪崩：TTL 加随机、Redis 高可用。
项目目前只做了 cache-aside，属于可改进项。

**Q：Redis 存了什么？**
会话 `vp_session_*`、视频详情 `cahce_video_*`（历史拼写）、播放/点赞计数 `video_count_*`、
用户统计 `user_count_*`、URL 权限、用户身份角色。

## 6. 数据库 / ORM 追问

**Q：为什么用 ODB 而不是手写 SQL？**
实体与表结构同源（`#pragma db`），编译期检查字段，生成 schema 与查询代码，换数据库只改 profile；
连接池直接用 `connection_pool_factory`。代价是学习曲线和生成代码的构建复杂度。

**Q：事务怎么用？**
每个业务方法里 `odb::transaction mtx(db->begin())`，RAII 提交/回滚；跨服务一致性用「本地事务 + MQ 最终一致」。

**Q：视频状态机？**
`待审核(1) → 上架(2) / 驳回(3)`，下架(4)，转码中(5)/失败(6)；审核通过写 `auditor_uid`。

## 7. 文件与转码追问

**Q：为什么用 FastDFS？**
视频/切片量大、单机存不下，FastDFS 的 Tracker/Storage 架构可水平扩容；业务只存 `file_id`，不关心路径。
替代品：MinIO/Ceph（S3 兼容，生态更好），课程选 FastDFS 是为了练手。

**Q：转码具体做了什么？**
下载源文件 → FFmpeg 打开输入、复制编码参数（`avcodec_parameters_copy`）、以 `hls` 封装输出
（`hls_time=10`、`hls_playlist_type=vod`）→ 生成 m3u8 + ts → 上传 FastDFS → 把视频的 `video_fid` 换成 m3u8 的 id。
注意：这是 **remux（不重编码）**，所以快；要改分辨率/码率才需要 x264 重编码。

**Q：HLS 和 RTMP 的区别？**
HLS 基于 HTTP、切片传输、兼容性好、延迟高（秒级），适合点播/大规模分发；
RTMP 基于 TCP 长连接、延迟低，适合直播推流。点播用 HLS。

**Q：m3u8 里的 ts 地址怎么来的？**
转码时设置 `hls_base_url=/HttpService/downloadVideo/?fileId=`，FFmpeg 会把每个分片的 URL 写成
「base_url + 上传后的 file_id」，客户端按行解析即可。

## 8. 工程与排错（真实经历，最能加分）

**Q：讲一个你排查过的 bug。**
- 链接期 `undefined reference to pplx::get_ambient_scheduler`：etcd 客户端头文件用到 cpprest 的 future，补链 `cpprest`；
- `odb::boost::date_time` 未定义：用了 date-time profile，补链 `odb-boost`；
- 二进制找不到 `libavformat.so.58` / 间接依赖 `libgme.so.0`：FFmpeg 装在私有前缀，
  一开始只加 `RUNPATH`，但 RUNPATH 不传递给间接依赖，改成 `-Wl,--disable-new-dtags` 生成 `DT_RPATH` 解决；
- ES 未启动导致 video 服务 `abort()`：改成捕获异常 + `_enabled=false` 降级，搜索返回空、其他功能正常；
- 某次重启后 video 卡在 MQ 声明：`condition_variable` 无超时，声明失败时永久等待，加 30s 超时并快速失败；
- 网关偶发 `SERVICE_NOT_FOUND`：① etcd 租约 3s 在高负载下过期，服务反复上下线；② 重启后同地址的新旧实例，
  旧 key 到期删除时把新实例的地址也移除了。修复：租约 10s、先建 watch 再全量拉取、
  节点表按 etcd 实例键跟踪（同地址还有其它实例就保留信道）、每 5s 周期性全量同步兜底；③ 用户服务还因一条日志格式参数不匹配（`{}` 多于实参）触发 spdlog 异常链，
  修复日志 + 设置 spdlog 错误处理器只打印不抛出。

**Q：怎么验证系统是好的？**
单元测试（gtest 8 项：JSON/字符串/随机串/文件/M3U8/密码哈希）+ 冒烟脚本（网关/会话/列表）+
curl 端到端链路（上传→转码→HLS→列表→点赞/弹幕→审核上下架）。

## 9. 高并发与优化（被追问时的方向）

**本机基线（可复现）**：2 vCPU / Debug 构建，`allVideoList` 20 并发 276 QPS（p50 68ms），
50 并发 290 QPS（p99 346ms）；加首页列表 3s 短缓存后提升到 **765/804 QPS**（p99 94ms），
约 **2.8 倍**，详见 [05-performance.md](05-performance.md)。

1. **网关**：多实例 + 负载均衡；brpc 连接池复用；限流（令牌桶）与熔断；
2. **缓存**：热点视频本地缓存 + Redis 集群；计数用 Redis 原子操作（`INCR`），已具备；
3. **数据库**：读写分离、分库分表（按 video_id）；列表查询加索引、避免深分页；
4. **MQ**：批量回写、消费者多线程、失败重试与死信；
5. **文件**：FastDFS 扩容 Storage 组；切片走 CDN；
6. **转码**：任务队列分级、GPU 编码、失败重试；
7. **可观测**：接入 Prometheus（brpc 自带 bvar 指标）+ 链路追踪。
